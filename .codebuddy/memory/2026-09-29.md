## 追问：数据库初始化能不能一起脚本化（2026-09-29）

**能** —— 这仓库其实只差把 `docs/HANDOVER.md` 第 5 节「首次部署」那 6 步串起来，每一步都是纯 CLI：

- `wrangler d1 create` / `kv namespace create` / `r2 bucket create` 都能非交互跑（`--json` 可解析出 id），
  再用正则把 id 写回 `wrangler.toml`（`REPLACE_WITH_*` 占位符）；
- `wrangler secret put NAME` 支持从 stdin 喂值（`'值' | npx wrangler secret put NAME`）；
- `POST /api/admin/bootstrap` 就是一次 curl（带 `RECOVERY_TOKEN` 与 `seedContent`）。
- 现成可复用：`npm run db:migrate:remote`（= `scripts/migrate.ps1 -Target remote`）。

**想放进 Workers Builds 一起跑，有三道坎**：
1. 自动生成的构建 token 权限里**没有 D1**（只有 Workers Scripts / KV / R2 edit + Worker Routes）→ 必须在构建配置里放**自定义 token**（官方支持自定义/复用 token）；
2. 构建镜像是 Ubuntu 24.04，**没有 pwsh** → 现有 `scripts/migrate.ps1` 在 CI 里跑不了，得写 Node 版
   （顺带解决它「每次把所有文件跑一遍、靠容忍 already exists」的问题：Node 版可用一张 `_migrations` 表做真幂等）；
3. 迁移要放在 **deploy 命令**里、且在 `wrangler deploy` **之前**，否则新代码先于 schema 上线。

**当时给用户的建议（尚未落地）**：初始化与迁移留本地一次性脚本，CI 只做 build + deploy；
若要 CI 跑，则需幂等的 Node 迁移脚本 + 自定义 token + `SKIP_MIGRATE` 之类开关。

## 追问 2：能不能「用别名绑定」，让用户自建 D1/KV/R2（2026-09-29，已在本机实测）

用户想法：用户自行创建 D1/R2/KV，项目通过「别名」绑定，仓库里不带别人的 ID。**结论：R2 成立，KV/D1 没有名字式绑定；但 ID 现在可以不写（自动创建）。**

- 本机 **wrangler 4.137.0** 的 `config-schema.json` 实测：`d1_databases` / `kv_namespaces` / `r2_buckets` 三者的
  `required` **都只有 `binding`** —— 即 `database_id` / `id` / `bucket_name` 现在都能省（这就是官方文档
  「Automatic provisioning」那一节的机制）。
- 实测二：写一份只有 `binding`（+ D1 的 `database_name`、R2 的 `bucket_name`）的临时配置跑
  `wrangler deploy --dry-run --config ...` → **exit 0**，绑定表正常列出
  （`env.DB (kingcola-db) D1 Database` / `env.CONFIG_KV KV Namespace` / `env.FILES (kingcola-files) R2 Bucket`）。
- 但要分清三件事：
  1. **只有 R2 是「名字式」绑定**（按 `bucket_name`）；KV 只有 `id`、D1 靠 `database_id`（`database_name` 只是可读标识）。
  2. **自动创建 ≠ 复用你自建的那套**：它会**新建**资源，名字以 Worker 名作前缀 → 「用户自建」与「不写 ID」是两条**互斥**路线。
  3. **回写行为**：`wrangler deploy`（本地）会把自动创建的 ID **写回 `wrangler.toml`**（会变成工作区改动）；
     而**从 Dashboard/Git 构建部署时 ID 不回写仓库**，只能在 Dashboard 看。
- ⚠️ **配置文件是绑定的唯一事实源**：4.137.0 的 schema 里**只有 `keep_vars`、没有 `keep_bindings`** →
  想在 Dashboard 里按名字配好绑定、代码里不写，下次部署会被覆盖（secrets 例外，wrangler 不删 secret）。
- ⚠️ 顺带发现（本项目既有隐患）：**绑定不可被 env 继承**，而 `[env.preview]` 只重写了 `name` 与 `SSO_AUTHORIZE_BASE`，
  **没有重写 D1/KV/R2** → 若开预览构建，预览 Worker 实际是**没有这些绑定**的。
- 迁移不受影响：`scripts/migrate.ps1` 是按**数据库名**执行的（`d1 execute kingcola-db --file=`），没有 ID 也能跑。

## 「恢复口令不正确」的真实根因（重要坑）+ 两个 Worker 的问题

用户在 `/admin` 用我给的初始化口令，得到 `403 INVALID_TOKEN 恢复口令不正确`，并怀疑「搞错项目了」。

**排查手段（可复用）**：bootstrap 是**先验口令、后验密码**，所以可以 `POST /api/admin/bootstrap`
带上**真实口令 + 1 位密码**做**非破坏性校验** —— 返回 `400 WEAK_PASSWORD` 说明口令通过，
返回 `403 INVALID_TOKEN` 说明口令不对；两种情况都**不会建号**。

**根因（实测确认）**：`'值' | wrangler secret put NAME`（PowerShell 管道喂值）会把**换行一起存进去**，
于是库里存的是 `值\n`，浏览器手输的值永远对不上 → 一律 403。
**换成 `wrangler secret bulk <json>`（值写在 JSON 字符串里，不带换行）后立刻通过**
（复验：`400 WEAK_PASSWORD` = 口令已通过；之后 `initialized` 仍为 false，说明没有误建号）。
→ 这个坑已写进 README 的密钥一节。

时间点像是 Git 构建 —— 怀疑用户在面板重建/新开了项目，其构建被 CI 的名字覆盖机制部署到 `-home2`）、
以及无关的 `frey-cloud-game*`、`workerchat-with2`。
